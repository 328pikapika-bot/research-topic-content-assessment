# context-incremental-sync

这个 skill 用来把当前对话和执行结果 **按“每个问题一个单元”持续增量同步** 到 `E:\all-context` 目录下的 Markdown 档案文件中。

它的重点不是“写一段总总结”，而是把：

- 用户原话
- 模型如何理解这个问题
- 模型为了解决这个问题做了什么
- 最终得到什么结论或执行结果
- 涉及哪些文件变更

逐条沉淀下来，方便后续查历史、接着做、或者回看某一个具体问题是怎么处理的。

## 什么时候使用

当用户出现下面这类需求时，优先使用这个 skill：

- 把这次对话同步到 `docs/上下文/context.md`
- 把本会话历史所有问题补到 context 文件里
- 以后每次处理都往 context 文件里追加
- 按每个问题整理本次会话
- 记录用户原话和模型处理逻辑
- 记录本次修改了哪些文件、改了哪几行
- 把本次结论、风险、待办写进项目上下文
- 把历史对话补录到 `D:/.../docs/上下文/context.md`

## 核心原则

1. 凡是调用这个 skill 生成的 Markdown 文件，一律写入 `E:\all-context`。
2. 文件名一律采用：`<问题摘要>-<时间>-<工具名>.md`。
3. 工具名必须明确；Claude Code 调用时写 `claudecode`，Codex 调用时写 `codex`。
4. 只能追加，不能覆盖，不允许删除历史内容。
5. **一个用户问题 = 一个记录单元**，不要把整段会话压成一条大记录。
6. 如果用户要求“把本会话历史所有问题都更新进去”，必须按问题出现顺序拆成多条记录逐条追加。
7. 每个问题单元之间必须使用分割线 `---` 分开。
8. 每个问题单元都必须带时间；至少要有 `记录时间`，如果知道精确提问时间，再补 `原始提问时间`。
9. 用户原话必须 **一字不差** 保留，不要改写。
10. 不只记录结论，还要记录 **模型处理逻辑**：为什么这样理解、为什么先看哪个文件、为什么先查数据库、为什么暂时不执行某一步。
11. 执行动作、执行结果、修改文件、新增文件、删除文件、风险待办都要结构化记录。
12. 如果本次没有文件变更，也要明确写“本次无文件变更 / 无新增文件 / 无删除文件”。
13. 如果是对历史问题做补充，必须继续追加新单元，不要回头覆盖旧记录。
14. 如果用户要求按问答形式整理，必须显式写出“问（用户原话）”和“答（模型回答 / 本轮结果）”。
15. 如果用户要求区分工具，必须明确写出当前使用的是 `claudecode`、`codex` 或其他工具，不能省略。
16. 如果内容涉及代码、页面、设计或具体实现，必须补充模块、页面入口、代码文件、方法名、调用链或关键代码位置，不能只写抽象结论。
17. 为了让 Markdown 左侧标题或目录可见，每个问题单元默认都要在最上方增加一个导航标题，必须使用 H3 标题，推荐格式为 `### 问题序号-问题主题`。
18. 如果用户明确说“要有总结”或“要在标题里看到这一项”，则至少要保证 H3 导航标题存在；如需补充说明，可在导航标题下方紧跟一段 `摘要：...`，用 1 到 3 段话概括该问题的目标、处理结果和边界。

## 统一归档目录模式

调用该 skill 时，生成的 Markdown 档案统一放在 `E:\all-context`，按下面规则处理：

1. 档案文件直接放在 `E:\all-context` 根目录下，默认使用 `.md` 格式。
2. 文件名采用：`<问题摘要>-<时间>-<工具名>.md`
3. 工具名必须明确；Claude Code 调用时写 `claudecode`，Codex 调用时写 `codex`。
4. 时间字段用于文件名中的归档时间，推荐精确到分钟。
5. 如果是同一个窗口 / 同一条持续会话的后续补录，应继续追加到第一次创建的对应文件中，不重复新建同主题文件。
6. 这种集中历史目录中的文件允许使用绝对路径描述归档位置，便于跨项目检索。

## 记录粒度规则

### 默认粒度

默认按 **每个用户消息** 作为一个问题单元记录。

### 拆分粒度

如果同一条用户消息里明确包含多个独立问题，并且用户希望“按问题逐条整理”，则应进一步拆分，例如：

- 用户自己用了编号 `1、2、3`
- 同一条消息里是多个明显独立的提问
- 用户明确要求“每个问题单独记录”

不要机械地按逗号乱拆；要以“后续能独立回看和追踪”为准。

## 时间记录规则

### 每条记录至少包含一个时间

每个问题单元都必须至少包含：

- `记录时间`：本次把这条记录写入 context 文件的时间，精确到分钟

### 能拿到原始提问时间时

如果能拿到该问题的原始提问时间，再额外记录：

- `原始提问时间`：用户最初提出该问题的时间，精确到分钟

### 拿不到原始提问时间时

不要伪造历史精确时间。此时：

- 仍然必须记录 `记录时间`
- 可以补充说明 `原始提问时间未提供，本次按记录时间补录`

## 推荐记录格式

每个问题单元单独追加，建议使用下面结构：

```markdown
---
问题序号-关联问题(前面内容要做标题h3标题显示)
问题序号：1
记录时间：YYYY-MM-DD HH:mm
原始提问时间：YYYY-MM-DD HH:mm（如未知可省略，或写明未提供）
关联问题：第 1 题（仅补充历史记录或继续跟进某个旧问题时使用）

用户原话：
<原样保留>

模型处理逻辑：
- 我如何理解这个问题
- 为什么先看某个目录、模块、配置、数据库
- 为什么先回答问题而不是立即执行
- 为什么把它归类到某个前端 / 后端 / 数据问题

执行动作：
- 读取了哪些文件
- 检查了哪些配置
- 执行了哪些命令 / 查询 / 脚本
- 如果本轮只分析未落地，也要明确写出

结果 / 结论：
- 得到了什么结论
- 是否已执行完成
- 如果没做完，卡在哪一步

修改文件：
- relative/path.ext ｜ 行号/区段：... ｜ 说明：...

新增文件：
- relative/path.ext ｜ 整文件新增 ｜ 说明：...

删除文件：
- relative/path.ext ｜ 整文件删除 ｜ 说明：...

备注 / 风险 / 待办：
- ...
```

## “整段会话历史补录”规则

当用户说：

- 把这个会话里的历史所有问题都更新到 context
- 把本会话前面问过的内容都补进去
- 重新按历史问题整理到 context 文件

此时不要写成“一个大汇总块”。

正确做法是：

1. 回看本会话中用户已经提出的历史问题。
2. 按问题出现顺序整理。
3. 每个问题生成一个独立单元。
4. 每个单元单独写：用户原话、模型处理逻辑、执行动作、结果、文件变更、备注。
5. 多个问题单元连续追加到同一个 context 文件末尾。
6. 如果 context 文件里已经存在同一批历史问题，优先补充缺失项，不要整段重复追加。

## “增量补充”规则

这个 skill 是 **append-only** 的。

### 新问题

出现新问题时，直接在文件末尾新增一个问题单元。

### 旧问题有新进展

如果是对旧问题继续推进，不要回头改旧块，而是继续追加一个新单元，并写清楚：

- 这是对哪个问题的补充
- 本次新增了什么判断、动作、结果
- 本次涉及哪些文件或数据变化

例如可写：

- `关联问题：第 3 题`
- `本次为第 3 题的继续处理`

### 历史问题批量补录

如果用户后面又要求“把前面整个会话历史补进去”，应先检查文件末尾，避免把已写过的问题整批重复追加。

## 文件变更记录规则

### 路径要求

- 所有由该 skill 生成的 Markdown 档案统一写入 `E:\all-context`。
- 文档中的文件变更路径可以根据场景记录为相对路径或绝对路径；若为了后续检索需要标明归档位置，可使用绝对路径。

### 行号要求

优先级如下：

1. 精确单行，例如 `行 24`
2. 代码区段，例如 `行 24-46`
3. 无法精确时写明原因，例如 `文件末尾追加`、`区段级变更，未精确到单行`
4. 整文件新增 / 整文件删除

不要伪造精确行号。

### 无文件变更场景

如果本次只是分析、讨论、查库、给方案、口头确认，没有真实文件改动，也必须明确写：

```markdown
修改文件：
- 本次无文件变更

新增文件：
- 本次无新增文件

删除文件：
- 本次无删除文件
```

## 路径处理规则

- 输出 Markdown 档案时，不再写项目内 `context.md`，统一写入 `E:\all-context`。
- 如果用户在描述里给了其他 context 文件路径，仍应在记录或回复中说明该请求，但最终归档文件要落到 `E:\all-context`。
- 如果用户提供的问题摘要不适合作为文件名，应先规范化为可读、可检索的短标题，再参与文件名拼装。
- 一旦实际写入路径与用户原句不完全一致，要在记录或回复中说明最终使用的真实路径。
- 如果需要自动生成文件名，则按：`问题摘要-时间-工具名.md`。
- 工具名必须使用归一化结果：Claude Code=`claudecode`，Codex=`codex`。

## 执行流程

### 第一步：确定目标归档文件

- 归档目录固定为 `E:\all-context`
- 文件名固定采用 `问题摘要-时间-工具名.md`
- 如果指定文件不存在，可以创建
- 如果文件已存在，只允许追加，不能覆盖

### 第二步：确定记录模式

先判断当前任务属于哪一种：

1. **当前问题即时追加**
2. **本会话历史问题批量补录**
3. **对旧问题做增量补充**

不同模式都只能追加，不能回写旧内容。

### 第三步：按问题单元收集内容

每个问题单元至少收集这些字段：

- 问题序号（建议）
- 记录时间（必须）
- 原始提问时间（能拿到就写）
- 用户原话（必须原样保留）
- 模型处理逻辑
- 执行动作
- 结果 / 结论
- 修改文件
- 新增文件
- 删除文件
- 备注 / 风险 / 待办

注意：

- `用户原话` 不能改写
- `模型处理逻辑` 不能只写一句“已处理”，要体现思路
- `执行动作` 要体现实际查了什么、做了什么
- `结果 / 结论` 要体现当前状态，而不是重复动作本身

### 第四步：规范化追加

优先使用技能自带脚本，避免手工拼接格式不一致。

脚本支持两种写法：

1. **单问题追加**：一次追加一个问题单元
2. **多问题批量追加**：一次把本会话历史多个问题按 `entries` 数组批量追加

## 推荐脚本用法

### 单问题追加

```bash

{
  "record_time": "2026-04-27 17:06",
  "question_index": 1,
  "question_time": "2026-04-27 16:40",
  "user_raw": "前端用户如何创建一个未提交的数据，能不能直接连接数据库帮我创建一个假数据？",
  "processing_logic": [
    "识别出用户的问题分成两部分：前台如何制造未提交数据，以及是否可直接通过数据库造数。",
    "先回答当前是否能操作数据库、当前用的是什么库，再决定是否执行造数。"
  ],
  "actions": [
    "检查数据库连接配置与当前生效数据源。",
    "确认账号映射关系和造数所需主子表。"
  ],
  "result": [
    "已确认数据库可操作，并定位到用户账号对应的前台用户信息。"
  ],
  "modified_files": [
    {"path": "doc/data/事务功能/context.md", "location": "文件末尾追加", "note": "记录该问题的分析与执行结果"}
  ],
  "added_files": [],
  "deleted_files": [],
  "notes": [
    "如需继续为该问题补充处理结果，后续追加新单元，不覆盖本条。"
  ]
}
EOF
```

## 信息不完整时的处理

- 缺少文件变更信息：先记录已知部分，并明确“文件变更信息待补充”。
- 没有精确历史提问时间：不要伪造，写 `记录时间`，并说明原始提问时间未提供。
- 用户只要求记录对话，不要求记录文件变更：也要明确写“本次无文件变更”。
- 用户要求补录整段会话：按问题拆开，不要压成一条总记录。

## 禁止事项

- 不要覆盖已有 context 内容。
- 不要把整个会话只写成一条“汇总记录”。
- 不要改写用户原话。
- 不要省略模型处理逻辑，只留下结果。
- 不要为了显得完整而编造历史精确时间。
- 不要伪造文件变更行号。
- 不要省略“本次无文件变更 / 新增 / 删除”这一事实。
- 不要把追加记录写成松散自然语言，导致后续难以检索。
